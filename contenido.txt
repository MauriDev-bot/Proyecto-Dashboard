
# Introducción completa al Desarrollo Web de APIs en Python

## 1. ¿Qué significa desarrollar APIs?

Una **API** (*Application Programming Interface*) es una interfaz que permite que dos sistemas se comuniquen.

Por ejemplo:

```text
Aplicación móvil
       │
       │ HTTP
       ▼
┌──────────────────┐
│    API Python    │
│     FastAPI      │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│    PostgreSQL    │
└──────────────────┘
```

Imagina una aplicación de una biblioteca.

El frontend podría necesitar:

```text
Ver libros
Crear usuarios
Registrar préstamos
Buscar libros
Iniciar sesión
```

En lugar de conectarse directamente a la base de datos, realiza peticiones a una API:

```text
GET /libros
POST /usuarios
POST /login
POST /prestamos
```

La API recibe esas peticiones, ejecuta la lógica correspondiente y devuelve normalmente información en **JSON**.

HTTP funciona bajo un modelo cliente-servidor y es la base de gran parte de estas comunicaciones web.

# 4. HTTP: el concepto más importante antes de una API

Una API web normalmente recibe **peticiones HTTP**.

Una petición podría verse conceptualmente así:

```http
GET /usuarios/25 HTTP/1.1
Host: api.ejemplo.com
Authorization: Bearer TOKEN
```

La API podría responder:

```json
{
    "id": 25,
    "nombre": "Manuel",
    "activo": true
}
```

HTTP define métodos con diferentes propósitos.

Los principales son:

| Método | Propósito típico |
|---|---|
| GET | Obtener información |
| POST | Crear información |
| PUT | Reemplazar completamente |
| PATCH | Modificar parcialmente |
| DELETE | Eliminar |
| OPTIONS | Consultar opciones de comunicación |

Ejemplo:

```text
GET    /usuarios
GET    /usuarios/10
POST   /usuarios
PATCH  /usuarios/10
DELETE /usuarios/10
```

Esto ya comienza a parecerse a una **API REST**.

# 5. Códigos HTTP

Las respuestas HTTP contienen códigos de estado.

Se agrupan en cinco familias: `1xx`, `2xx`, `3xx`, `4xx` y `5xx`.

Al desarrollar APIs utilizarás constantemente:

```text
200 OK
201 Created
204 No Content

400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content

500 Internal Server Error
```

Ejemplo:

```text
POST /usuarios
```

Si funciona:

```http
201 Created
```

Si intentas obtener un usuario inexistente:

```http
404 Not Found
```

Un buen backend no devuelve simplemente:

```json
{"error": "algo salió mal"}
```

para absolutamente todos los errores.

Debe utilizar correctamente HTTP.

# 14. Ejemplo CRUD completo básico

```python
from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel, Field


app = FastAPI()


class UsuarioCrear(BaseModel):
    nombre: str = Field(min_length=2, max_length=80)
    edad: int = Field(ge=0, le=120)


class Usuario(UsuarioCrear):
    id: int


usuarios: dict[int, Usuario] = {}


@app.get("/usuarios")
def listar_usuarios():
    return list(usuarios.values())


@app.get("/usuarios/{usuario_id}")
def obtener_usuario(usuario_id: int):

    usuario = usuarios.get(usuario_id)

    if not usuario:
        raise HTTPException(
            status_code=404,
            detail="Usuario no encontrado"
        )

    return usuario


@app.post(
    "/usuarios",
    response_model=Usuario,
    status_code=status.HTTP_201_CREATED
)
def crear_usuario(datos: UsuarioCrear):

    usuario_id = len(usuarios) + 1

    usuario = Usuario(
        id=usuario_id,
        **datos.model_dump()
    )

    usuarios[usuario_id] = usuario

    return usuario


@app.delete(
    "/usuarios/{usuario_id}",
    status_code=status.HTTP_204_NO_CONTENT
)
def eliminar_usuario(usuario_id: int):

    if usuario_id not in usuarios:
        raise HTTPException(
            status_code=404,
            detail="Usuario no encontrado"
        )

    del usuarios[usuario_id]
```

Aquí ya aparecen varios conceptos importantes:

```text
Rutas
Métodos HTTP
Modelos
Validación
Códigos HTTP
Errores
CRUD
response_model
```

Pero todavía estamos utilizando memoria RAM.

Al reiniciar el servidor:

```text
todos los usuarios desaparecen
```

Necesitamos una base de datos.

# 16. ORM

ORM significa:

**Object Relational Mapper**.

Permite trabajar con tablas mediante objetos Python.

Sin ORM podrías escribir:

```sql
SELECT * FROM users WHERE id = 5;
```

Con un ORM conceptualmente puedes hacer algo parecido a:

```python
usuario = session.get(User, 5)
```

Uno de los ORMs/ecosistemas SQL principales de Python es:

```text
SQLAlchemy
```

Su tutorial oficial cubre tanto SQLAlchemy Core como su ORM y conceptos como conexiones, transacciones, metadatos y consultas.

# 17. Modelos de base de datos frente a schemas

Hay una distinción profesional importante.

## Modelo de base de datos

Describe cómo guardas información.

```python
class User:
    id
    email
    password_hash
    created_at
```

## Schema de entrada

Describe lo que permites recibir.

```python
class UserCreate:
    email
    password
```

## Schema de respuesta

Describe lo que entregas.

```python
class UserResponse:
    id
    email
    created_at
```

Nunca deberías devolver:

```text
password
password_hash
secret keys
tokens privados
```

por accidente.

# 19. Router

En lugar de colocar 100 endpoints en `main.py`, puedes separarlos.

Por ejemplo:

```python
from fastapi import APIRouter


router = APIRouter(
    prefix="/usuarios",
    tags=["Usuarios"]
)


@router.get("/")
def usuarios():
    return []
```

Posteriormente:

```python
app.include_router(router)
```

Esto permite construir una aplicación modular.

# 20. Servicios

Una ruta HTTP no debería contener toda la lógica.

En vez de:

```python
@app.post("/usuarios")
def crear_usuario():
    # 80 líneas de código
```

podemos hacer:

```python
@app.post("/usuarios")
def crear_usuario(datos: UsuarioCrear):
    return usuario_service.crear(datos)
```

Entonces:

```text
Controller / Route
       ↓
Service
       ↓
Repository
       ↓
Database
```

Esta separación mejora:

```text
mantenimiento
testing
reutilización
legibilidad
escalabilidad
```

# 23. Autenticación vs autorización

Son conceptos distintos.

### Autenticación

Responde:

> ¿Quién eres?

Ejemplo:

```text
usuario = manuel
```

### Autorización

Responde:

> ¿Qué puedes hacer?

Ejemplo:

```text
Usuario normal:
GET /productos

Administrador:
POST /productos
DELETE /productos
```

Puedes tener:

```text
RBAC
Role Based Access Control
```

Roles:

```text
user
editor
admin
superadmin
```

# 24. Seguridad de APIs

Una API profesional debe considerar seriamente la seguridad.

OWASP mantiene un proyecto específico dedicado a riesgos de seguridad de APIs. Entre los riesgos de su lista se encuentran problemas de autorización por objeto, autenticación rota, consumo sin restricciones de recursos, SSRF, configuraciones incorrectas e integración insegura con APIs externas.

Como mínimo deberías estudiar:

```text
Validación de entradas
Autenticación
Autorización
HTTPS
CORS
Rate limiting
Gestión de secretos
SQL Injection
NoSQL Injection
BOLA / IDOR
SSRF
Logging
Actualización de dependencias
```

Por ejemplo, que exista:

```text
GET /facturas/100
```

no significa que cualquier usuario autenticado deba poder consultar la factura `100`.

Hay que comprobar:

```text
¿Esta factura pertenece realmente al usuario?
```

# 27. APIs externas

Tu backend también puede ser cliente de otra API.

Arquitectura:

```text
Frontend
   │
   ▼
Tu API
   │
   ├──── API meteorológica
   │
   ├──── API de pagos
   │
   └──── API de correo
```

Por ejemplo:

```python
import httpx


async def obtener_datos():

    async with httpx.AsyncClient() as client:
        response = await client.get(
            "https://api.example.com/data"
        )

    response.raise_for_status()

    return response.json()
```

En aplicaciones profesionales necesitas además:

```text
timeouts
retries
manejo de errores
circuit breakers
logging
validación de la respuesta
```

No se debe confiar ciegamente en los datos provenientes de terceros; OWASP también identifica el consumo inseguro de APIs como un riesgo específico.

en una imagen reproducible.

La guía oficial de Docker para Python incluye específicamente contenerización de aplicaciones Python y un ejemplo con FastAPI.

Un `Dockerfile` simplificado podría ser:

```dockerfile
FROM python:3.13-slim

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["fastapi", "run", "main.py", "--port", "8000"]
```

Después:

```bash
docker build -t mi-api .
```

Y:

```bash
docker run -p 8000:8000 mi-api
```

Docker empieza a ser especialmente interesante cuando tu proyecto tiene:

```text

worker
```

y utilizas Docker Compose.

# 36. Migraciones

Supongamos que inicialmente tienes:

```text
users
 ├ id
 └ email
```

Pero después necesitas:

```text
users
 ├ id
 ├ email
 ├ username
 └ created_at
```

No deberías eliminar manualmente la base de datos cada vez.

Para SQLAlchemy es frecuente utilizar:

```text
Alembic
```

para mantener migraciones versionadas.

Conceptualmente:

```text
Código versión 1
Database versión 1

        ↓ migration

Código versión 2
Database versión 2
```

# 37. Redis y caché

Imagina que tienes:

```text

```

y calcularlas tarda:

```text

```

pero cambian únicamente cada hora.

Puedes guardar temporalmente el resultado:

```text
API
 ↓
Redis
 ↓
si existe → devolver

si no:
 ↓
Database
 ↓
calcular
 ↓
guardar en Redis
```

Redis también puede utilizarse para:

```text
caché

sesiones
colas
datos temporales
```

      ▼

      │
      ▼

      │
      ▼
procesamiento

Muchas arquitecturas modernas también utilizan Redis o RabbitMQ como intermediarios.

# Conclusión

Aprender APIs en Python no consiste solamente en aprender FastAPI.

El verdadero camino es:

```text
Python
  ↓
HTTP
  ↓
REST
  ↓
FastAPI
  ↓
Pydantic
  ↓
SQL
  ↓
PostgreSQL
  ↓
SQLAlchemy
  ↓
Autenticación
  ↓
Seguridad
  ↓
Testing
  ↓
Docker
  ↓
CI/CD
  ↓
Cloud
  ↓
Observabilidad
  ↓
Arquitectura profesional
```

FastAPI constituye un excelente punto de entrada porque combina validación mediante tipos, desarrollo moderno de APIs y generación automática de documentación OpenAPI. Su propia documentación oficial está organizada progresivamente desde primeros pasos hasta material avanzado.

El objetivo final no debería ser simplemente poder decir:

> «Sé FastAPI».

Sino poder recibir un requisito como:

> «Necesitamos una API segura para gestionar usuarios, dispositivos y redes, conectada a PostgreSQL, documentada, probada y desplegada mediante contenedores».

y saber cómo diseñar, desarrollar, probar y desplegar el sistema completo.
